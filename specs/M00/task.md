## T1：建立统一执行契约的词汇、状态与边界

**文件：** `specs/M00/unified-execution-v1.md`
**依赖：** 无

**步骤：**
1. 写明 M00 是逻辑契约，后续子项目确定具体 Go 接口、存储和 TUI 布局。
2. 定义普通任务、目标工作项、运行、隔离候选、预览、接收凭据、目标验收的关系；区分运行完成、已接收、已验证。
3. 记录受信控制面、共享执行器、隔离区与正式产物的写入边界。

**验证：** 阅读该文档，能够指出每个状态由谁写入，且找不到 agent 直接改正式产物或自行写入“已验证”的路径。

## T2：写普通任务与目标工作项的完整路径

**文件：** `specs/M00/unified-execution-v1.md`
**依赖：** T1

**步骤：**
1. 以同一套 `Submit → Run → Review → Accept` 操作分别描述普通任务和目标工作项。
2. 为两类任务各写一个隔离候选生成、检查、接收前正式产物保持原样的具体场景。
3. 写清目标工作项如何由持久事实调度；接收后如何用确切版本进入独立复核，以及复核通过/未通过的状态。

**验证：** 按两条场景逐步追踪，均能走到接收凭据；目标路径还能走到独立验收结论，且普通任务无需目标记录。

## T3：写检查、人工强制接收与预览失效规则

**文件：** `specs/M00/unified-execution-v1.md`
**依赖：** T2

**步骤：**
1. 建立规则表，覆盖适用检查通过、失败或不可用，以及越界、授权问题、正式版本冲突。
2. 对每种情况写明用户所见差异和提示、普通接收条件、用户明确强制接收后的结果；明确 agent 无权代确认。
3. 写入“实际影响无法展示时不得要求盲目确认”、候选/预览/正式版本变化后旧确认失效的规则。
4. 写明强制接收由受信控制面执行和审计，不改变 agent 的沙箱权限。

**验证：** 逐行检查规则表，确认每种异常均有用户可见信息和决策结果；修改候选或正式版本后，旧决定不能用于接收。

## T4：写目标事实归属、强制接收后复核及恢复规则

**文件：** `specs/M00/unified-execution-v1.md`
**依赖：** T3

**步骤：**
1. 建立事实归属表，列出目标、验收条件、证据、待复核责任、agent 会话、工具输出与用户接收记录的拥有者和效力。
2. 写出长期目标正常复核通过、未通过和人工强制接收三条场景；强制接收后明确保持未验证并持久安排复核。
3. 描述中断/重试时接收幂等、事件与目标事实恢复；会话文本不能冒充验收证据。

**验证：** 从强制接收场景追踪到新复核责任，找不到由 `Receipt`、工具输出或 agent 自述直接产生“已验证”的步骤；重复同一决定不会再次应用变更。

## T5：写同一 TUI 的两条用户流程

**文件：** `specs/M00/unified-execution-v1.md`
**依赖：** T2、T3、T4

**步骤：**
1. 以同一入口绘制普通任务流程：发起、流式进度、候选差异与检查、用户确认、接收结果。
2. 绘制长期目标流程：进入目标、查看工作项与候选、审阅/强制接收、查看目标状态和证据入口。
3. 写明 TUI 重连如何从事件游标与正式事实恢复视图；不锁定控件布局。

**验证：** 两条流程均无需启动第二个 agent 程序；能从界面找到候选、被覆盖的限制、接收凭据、目标状态和证据入口。
