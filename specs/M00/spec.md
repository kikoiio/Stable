# M00 统一 Agent 执行契约 Spec

## 背景

Stable 已有长期目标、验收条件、证据和复核机制。mewcode 有通用 agent 与更完整的终端界面。直接搬入 mewcode 的执行入口会形成两套执行路径，也会绕过已确定的“隔离候选、检查后接收”规则。

本轮先明确一个统一执行流程：普通任务直接使用 agent，长期目标由 Stable 持续派发工作给同一套 agent 执行能力。两者的文件修改先形成隔离候选，正式成果只在接收后改变。M00 是契约与迁移规划阶段，不交付运行代码。

## 目标

- 写清普通任务与长期目标如何共用 agent 执行能力，以及两类执行上下文和记录的归属。
- 写清隔离候选、检查、用户强制接收、目标独立验收和后续复核的行为边界。
- 写清长期目标事实与 agent 会话的关系，以及共用终端界面的用户流程。
- 据此修订迁移规划和与之冲突的设计原则；首发范围为 Linux。

## 功能需求

- **F1 统一执行**：普通任务直接启动 agent；长期目标由 Stable 持续派发工作给同一套 agent 能力。每次执行有自己的上下文和记录。
- **F2 隔离候选**：两类任务的文件修改先形成隔离候选；接收前展示差异，正式文件不因 agent 操作直接改变。
- **F3 人工接收**：普通任务先运行适用检查，再由用户审阅差异、检查结果和冲突。用户可明确强制接收，包括检查失败、越界、授权或版本冲突；agent 无权自行强制接收。
- **F4 长期目标验收**：长期目标正常接收须按验收条件独立复检。人工强制接收可以更新产物，但目标保持未验证，并安排重新复核；不能据此生成“已达标”结论。
- **F5 持久事实**：目标、验收条件、证据和待复核状态由 Stable 持久维护；agent 会话、工具输出或自述不能代替这些事实。
- **F6 共用界面**：一个终端界面展示普通任务的执行与接收，以及长期目标的状态、候选和证据；用户无需切换到另一套 agent 程序。
- **F7 迁移边界**：迁移规划覆盖 mewcode 的全部已识别功能，标明接入顺序和行为调整；允许移除旧目标实现并重建，不承诺旧数据和命令兼容。

## 非功能需求

- **N1 结论可信**：执行完成、候选已接收和目标已验证是不同状态；人工强制接收不能伪装成独立验收通过。
- **N2 可追溯与可恢复**：候选、检查结果、用户确认及被覆盖的限制都须可追溯。中断或重试后，不能重复接收或错误恢复成“已验证”。
- **N3 隔离边界**：人工强制接收由受信的接收环节执行，不赋予 agent 逃出隔离区或自行扩大文件、凭据和网络访问的能力。
- **N4 决策信息完整**：确认前展示将应用的差异、检查失败、越界路径及版本冲突；无法展示实际影响时不能要求用户盲目确认。
- **N5 平台与规划一致性**：首发范围为 Linux。M00 修订后的迁移规划、设计原则与执行契约不得互相矛盾，并能逐项追踪到后续子项目。

## 不做的事

- M00 不迁移运行代码，不改终端界面、工具或目标存储；这些在后续子项目实施。
- M00 不删除旧数据或停用现有服务；“允许移除重建”是后续切换的边界。
- 不要求兼容旧命令或旧数据格式，也不在本阶段制定数据迁移程序。
- 不确定具体界面布局、函数接口或逐文件复制清单；各子项目在自己的技术设计中决定。
- 不把 macOS、Windows 支持纳入首发范围。

## 验收标准

- **AC1（F1）**：文档分别走通普通任务和长期目标的完整执行路径，明确两者调用同一套 agent 能力，并说明执行上下文如何区分。
- **AC2（F2）**：对两类任务各给出“生成候选→检查→接收”的场景；接收前正式文件保持原样。
- **AC3（F3）**：规则表覆盖检查通过、失败或不可用，以及越界、授权和版本冲突；每种情况都说明用户看到什么、如何明确强制接收，并明确 agent 不能代替用户确认。
- **AC4（F4）**：长期目标场景覆盖独立验收通过、未通过和人工强制接收；强制接收后状态仍为未验证，且有后续复核责任。
- **AC5（F5）**：事实归属表明确目标、验收条件、证据与 agent 会话的关系；示例中工具输出和 agent 自述均不能单独使目标变为已验证。
- **AC6（F6）**：界面流程稿从同一个终端界面入口分别走通普通任务和长期目标，并展示候选审阅、确认、目标状态与证据入口。
- **AC7（F7）**：迁移地图将已识别的 mewcode 功能逐项归到后续子项目，标出依赖、Linux 首发和允许移除重建的切换边界；相关规划与设计原则无相互矛盾的要求。
