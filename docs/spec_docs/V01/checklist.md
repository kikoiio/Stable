# V01 验收条件变化后的结论失效 Checklist

> 依据已批准的 [spec.md](spec.md)、[plan.md](plan.md) 和 [task.md](task.md)。开发完成后逐项执行；每项记录实际命令、输出或导出文件，再勾选。若环境阻止运行，应记录受限原因并在可运行环境补验，不把未运行视为通过。

## 用户可见行为

- [ ] **C01 / AC1：合法标准增加版本。** 对已有目标提出并确认一组合法新标准，读取确认前后状态；版本恰好增加一次，目标记录的新标准与确认内容一致。（验证：运行标准确认集成测试及 `tests/e2e/criteria_change.sh`，比较两次状态快照。）
- [ ] **C02 / AC1：无效标准不改目标。** 分别提交格式错误和不支持的标准，比较目标版本、状态、证据数量与内容；均保持不变，错误原因可见。（验证：运行标准校验与确认测试，比较确认前后快照。）
- [ ] **C03 / AC2：确认返回时已待复核。** 先让目标达标，再确认新标准并暂停新版检查；确认响应返回后立即查询状态与导出，均显示“待复核”、原因和新版本，当前达标为否。（验证：运行端到端脚本的暂停点，保存确认响应、状态 JSON 和导出 JSON。）
- [ ] **C04 / AC2、AC6：历史证据保留。** 在 C03 的暂停点查看旧证据；原记录仍可读取，原始检查结果保留，所属旧版本与失效原因可辨，不计入当前达标。（验证：比较确认前后证据 ID、结果和历史导出。）
- [ ] **C05 / AC3：新版证据出处完整。** 对 ERC 和连线验收项各完成一次新版检查；每条验收证据都能看到主张、覆盖范围、产物摘要、标准版本、检查器 ID 与版本、来源等级及失效依据。（验证：读取状态/导出的证据记录，逐字段核对；检查器版本与实际运行版本相符。）
- [ ] **C06 / AC3、N2：旧数据明确为未知。** 打开升级前的数据库并导出旧证据；缺失的标准或检查器信息显示为 `unknown`，旧行仍可读取，不被补写为新版已知出处。（验证：运行旧库迁移测试，并比较迁移前后旧证据行数及导出。）
- [ ] **C07 / AC4：已完成目标自动重新运行。** 对已达标且工作流已结束的目标确认新标准，不再发送用户指令；系统自行启动新一轮独立检查，并用新版证据更新结论。（验证：运行端到端脚本，核对确认后工作流和证据记录。）
- [ ] **C08 / AC4：先检查，未达标再修复。** 新标准初次检查失败但现有能力可处理时，观察到先有失败检查证据，再有既有修复动作，最后有重新检查的新版通过证据。（验证：运行传感器板场景，按时间比较检查、动作和复检记录。）
- [ ] **C09 / AC4：无法修复时说明缺口。** 让当前标准无法由现有能力满足；状态或回复列出未满足项和原因，并请求用户处理，当前达标保持为否。（验证：运行受控失败场景并检查状态、回复和导出。）
- [ ] **C10 / AC5：检查中再次改标准。** 暂停一次旧版检查，在其间确认更高版本，再放行旧版通过结果；最新版目标不得因此达标，之后按最新版标准产生新检查证据。（验证：运行受控并发测试及端到端暂停场景，按版本和时间核对状态变化。）
- [ ] **C11 / AC5：旧决策不得写入产物。** 在旧版决策产生后、动作执行前确认新标准；该动作被拒绝，产物前后摘要相同，最新版目标仍需重新检查。（验证：运行执行协调器竞态测试并比较文件摘要。）
- [ ] **C12 / AC6：全部当前标准均有证据。** 给同一目标设置 ERC 和连线标准；只提供其中一项通过证据时不能达标，两个当前验收项均由独立检查通过后才可达标。（验证：运行状态投影测试和端到端场景，比较两种证据集合的结果。）
- [ ] **C13 / AC6：当前与历史报告分开。** 标准版本或产物摘要变化后导出；旧 ERC 报告不出现在当前交付报告位置，若源文件仍在则可在历史部分查看并辨认版本与失效原因。（验证：比较变更前后导出目录及状态 JSON 中的报告路径。）

## 一致性、迁移与集成

- [ ] **C14 / AC7：确认期间中断可恢复。** 分别在确认事务前、提交后但唤醒前中断进程并重启；前者保持旧版本，后者为新版待复核并自动继续，不出现新版标准配旧版达标。（验证：运行崩溃边界测试，读取重启后的目标快照和事件状态。）
- [ ] **C15 / AC7：复核期间中断可恢复。** 在检查完成前后中断并重启 worker；未处理事件被补送，已处理事件不会造成重复当前结论，最终状态与最新版证据一致。（验证：运行 worker 重送及恢复测试，比较事件 ID、状态和当前证据。）
- [ ] **C16 / AC7：重复投递不重复确认。** 对同一确认提案或唤醒事件重复操作；版本只增加一次，当前目标不出现冲突状态。（验证：运行重复确认/事件测试并比较数据库快照。）
- [ ] **C17 / N3：数据契约与迁移一致。** 新库及升级后的旧库版本均为 3；两份契约分别标明存储 v3、证据 v1，实际字段和未知值解释与契约一致。（验证：查询 `PRAGMA user_version`，抽查一条新证据与一条旧证据，并对照契约文档。）
- [ ] **C18 / N4：达标只依赖独立检查。** 将模型文本、对话或截图作为唯一“通过”信息输入；状态仍为未达标，直到当前产物和标准对应的工具检查证据齐全。（验证：运行证据筛选与状态投影测试，对比注入前后 `verified` 值。）
- [ ] **C19 / 集成：模块交接完整。** 确认后持久事件能唤醒已结束目标；复核结果经版本守卫写入存储；状态和导出读到同一当前结论。（验证：运行 `tests/e2e/criteria_change.sh`，保存一次完整流程的事件、证据、状态和导出记录。）
- [ ] **C20 / 集成：原有行为仍可用。** 新建目标确认路径、原有传感器板检查与修复流程仍能完成；未更改标准的既有场景结果不回退。（验证：运行相关原有 Go/Python 测试和现有传感器板端到端脚本，比较结果。）

## 编译、测试与交付

- [ ] **C21：Go 全量测试通过。** 在允许本机 loopback 的 Linux 环境运行 `GOPROXY=off GOSUMDB=off go test ./...`，记录退出码和失败项；退出码为 0。（验证：保存完整测试输出。）
- [ ] **C22：KiCad 检查测试通过。** 运行 `python3 -m unittest discover -s workers/kicad -p 'test_*.py'`；ERC 阈值、检查器版本和报告错误场景均通过。（验证：保存测试输出与退出码。）
- [ ] **C23：端到端标准变更通过。** 在具备 KiCad、Temporal 和本机 loopback 的环境运行 `bash tests/e2e/criteria_change.sh` 及 `make e2e`；完整流程输出 PASS，未出现旧证据被计入新版达标。（验证：保存脚本日志与导出物。）
- [ ] **C24：交付不混入既有改动。** 比较 V01 提交与实施前记录的工作树基线；V01 提交只含本轮代码、测试和四份文档，原有未提交改动仍可逐项核对。（验证：查看提交差异、文件清单及实施前后的 `git status --short`。）

## 验收记录

执行时在每项下补充日期、命令、实际结果及证据位置；失败项保持未勾选，修复后重跑对应场景。最终报告逐项列出通过数量、未通过项及端到端实测结果。
