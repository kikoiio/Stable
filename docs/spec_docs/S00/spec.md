# S00 平台支持范围与能力契约 Spec

> 状态:已批准(2026-10-06)。S00 = 平台可移植性系列阶段 0(依据 docs/platform-portability-roadmap.md「阶段 0:定义支持范围和能力契约」),与 mewcode 迁移 M 系列分开编号。用户已确认:本阶段只声明 Linux(先解耦,macOS/Windows 顺序阶段 2 前再定);无头 ERC 检查是任何平台声明「支持」的前提,交互式 GUI 会话允许降级;产物落 docs/spec_docs/S00/;能力表采用单一文档形态(方案 A),验收条件编号化但不引入机器可读格式。

## 背景

Stable 当前可交付形态是 Linux x86_64 CLI/TUI:IPC 用 Unix domain socket 加 `chmod` 权限,单实例锁用 `syscall.Flock`,子进程管理依赖 `/proc` 与 POSIX 进程组,安全文件操作直接调用 `openat2`/`O_NOFOLLOW`/`RENAME_EXCHANGE`,沙箱依赖 bubblewrap 与 namespace,打包脚本固定 Linux x86_64。平台可移植性路线图(docs/platform-portability-roadmap.md)已给出六阶段解耦规划与实现盘点,但「一个平台算不算受支持」「每项能力在某平台处于什么状态、门槛是什么」尚无正式定义——没有这个定义,阶段 1–5 无法判断完成与否,也无法阻止「能编译但隔离或目录事务语义变弱」的版本被当作可交付。

阶段 0 是纯文档与决策阶段:产出支持范围声明、平台能力表、安全不变量与可执行验收条件,不改任何代码。本项为该阶段的规格(S00)。

## 目标

- **支持范围声明**:正式声明当前仅 Linux 受支持;macOS/Windows 列为「计划评估」,不绑定先后顺序(阶段 2 前再定)。
- **平台能力表**:路线图要求的 10 项能力 × 3 平台的状态矩阵;Linux 列以代码审计与可运行证据为据,作为后续所有阶段的回归基线。
- **安全不变量与能力不可用行为**:每项能力写明不可协商的安全保证,以及能力不可用时的 fail-closed 行为(向用户说明受限功能,不静默退化)。
- **可执行验收条件与发布门槛**:每行能力的验收条件编号化、可被阶段 1–5 直接引用;明确 KiCad 规则——无头 ERC 检查是任何平台声明「支持」的前提,交互式 GUI 会话允许降级标注。

## 功能需求

- F1 支持范围声明:文档开篇给出正式声明——当前仅 Linux(x86_64 CLI/TUI)为「受支持」;macOS 与 Windows 为「计划评估」,不承诺顺序与时限(阶段 2 前再定)。声明须说明「支持」的判定依据是能力表状态与发布门槛清单,且与矩阵内容不矛盾。
- F2 能力矩阵:包含路线图阶段 0 列出的 10 项能力行——①路径与安装布局 ②本机 IPC ③单实例锁 ④进程树托管 ⑤私密文件与安全存储 ⑥安全根目录访问 ⑦候选目录事务(原子验收) ⑧网络隔离(沙箱执行与网络授权) ⑨无头 KiCad 检查 ⑩交互式 GUI 会话。每行 × 每平台(Linux/macOS/Windows)给出且仅给出一种状态:支持 / 降级 / 不支持 / 未评估;Linux 列不得出现「未评估」。审计中若发现矩阵外的重要平台依赖点,允许增补行并标注「补充」。
- F3 Linux 现状基线(审计):每行的 Linux 状态须有证据支撑——引用至少一个代表性代码位置(文件级路径),并标注证据类型:可运行验证(附验证命令或测试名)/ 仅代码审阅。记录的是当前真实行为,不是目标行为。
- F4 安全不变量与能力不可用行为:每行能力写明两点——①至少 1 条安全不变量:该能力在任何平台实现都必须保持的不可协商保证(如:候选执行不得写入正式项目或未授权路径;私密配置不因平台权限模型扩大可读范围;进程停止不得误杀其他用户或不相关实例);②能力不可用行为:fail closed——禁用依赖该能力的功能,向用户说明受限原因,不静默退化为更弱的等价物。
- F5 可执行验收条件:每行能力附按状态等级的编号验收条件(如 AC-IPC-1):声明「支持」须满足哪些条目、声明「降级」须满足哪些条目。Linux 列的验收条件须在当前代码上可执行或映射到现有测试;编号一经使用不重命名,供阶段 1–5 直接引用。
- F6 macOS/Windows 列内容:状态统一为「未评估(计划评估)」;每行附已知等价机制线索(如 Windows 命名管道 ACL、Job Object),明确标注「未经验证,不构成承诺」。
- F7 发布门槛清单:列出任何平台从「未评估/降级」变更为「支持」前必须通过的事项(逐平台安全设计审查、隔离强度证明、事务崩溃一致性故障注入等);其中 KiCad 规则为:无头 ERC 检查必须可用,交互式 GUI 会话允许以「降级」状态存在。
- F8 完成标志对照:文档末尾逐条对照路线图「阶段 0 完成标志」(每项功能每平台状态明确 + 可执行验收条件;Linux 当前行为作为回归基线),逐条给出达成位置与证据。

## 非功能需求

- N1 一致性:声明、矩阵、不变量、验收条件四处对同一能力的描述不矛盾;术语与路线图、VISION 对齐。
- N2 可追溯:每条 Linux 状态可追溯到具体代码位置或可运行证据,引用精确到文件。
- N3 诚实性:未验证、不确定的内容显式标注(「仅代码审阅」「未经验证」),不得把假设写成已确认事实;审计若发现路线图盘点失实,记录差异并单独报告,不静默改写路线图。
- N4 可维护:矩阵结构稳定——增补行、增加平台列不破坏既有结构;验收条件编号稳定;文档为中文 Markdown。
- N5 版本跟踪:S00 四件套与能力表纳入 git 跟踪(为 docs/spec_docs/S00/ 增加 .gitignore 白名单条目),且不得改变 docs/ 内其他既有文件(如 spec_docs 下现有两份文档)的忽略状态。

## 不做的事

- 不修改任何产品代码与构建配置(含 build tags、目录调整、stub 实现)——属阶段 1 及以后。
- 不为 macOS/Windows 做版本/架构承诺、适配设计或等价机制评估——本阶段只留「未评估」状态与线索。
- 不产出平台 adapter 的接口设计——路径、IPC、锁、进程托管、安全文件、沙箱的接口定义属阶段 1(届时走各自规格)。
- 不构建机器可读能力表、CI 检查或 doctor 对照工具。
- 不修订路线图本身——审计发现的盘点失实之处以差异记录呈现,是否修订路线图由用户决定。
- 不动 docs/ 下其他文件的忽略状态,不把 spec_docs 现有两份文档纳入跟踪。

## 验收标准

- AC1(对应 F1):支持范围声明存在且明确——仅 Linux 受支持、macOS/Windows 为计划评估;声明与矩阵状态一致,无一处矛盾。
- AC2(对应 F2):矩阵含路线图要求的 10 行,每行 × 3 平台状态齐全且唯一(支持/降级/不支持/未评估四种取值);Linux 列无「未评估」。
- AC3(对应 F3):Linux 每行至少 1 个文件级代码引用 + 证据类型标注;「可运行验证」行附可执行命令或测试名,且抽验可跑通。
- AC4(对应 F4):每行 ≥1 条安全不变量 + 1 条能力不可用行为;行为均符合 fail closed 与向用户说明的要求。
- AC5(对应 F5):每行有按状态等级的编号验收条件;Linux 列条件在当前代码上可执行或映射到现有测试;编号无重复、无悬空引用。
- AC6(对应 F6):macOS/Windows 每行状态为「未评估(计划评估)」,且有等价机制线索及「未经验证」标注。
- AC7(对应 F7):发布门槛清单存在,且含 KiCad 无头必须 / GUI 可降级规则。
- AC8(对应 F8):完成标志对照表逐条给出达成位置与证据。
- AC9(对应 N5):`git ls-files` 可见 S00 全部文档;spec_docs 现有两份文档仍未被跟踪。
